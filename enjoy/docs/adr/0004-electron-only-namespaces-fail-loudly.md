# 浏览器够不着的 Electron 能力宁可报错，也不静默 no-op

浏览器侧的桥接实现要覆盖预加载脚本暴露的全部命名空间。其中五个在浏览器里没有对应物：文件对话框、外壳调用、内嵌浏览视图、应用生命周期、窗口控制。我们按分类降级：能合理映射的映射（打开外部链接、重载页面，以及浏览器本来就知道答案的那几个），够不着的返回一个**带方法名**的拒绝 Promise。

不采用静默 no-op。这是个自用工具，最难诊断的失败就是"点了没反应"——没有报错、没有日志、没有任何线索指向那一行代码。一个写着方法名的错误哪怕出现在控制台里，也比一次无声的返回值钱。

两类调用不算"静默 no-op"，因此照常返回：

- `on*` 与 `remove*Listeners` 这类订阅方法。标题栏与侧边栏在 effect 里订阅，effect 抛错会连带整个界面一起崩。它们照常注册到推送总线上——在浏览器里没有窗口事件可推，这是事实，不是被吞掉的调用。
- `view.show()` 与 `view.hide()`。这两个调用要求内嵌视图让开或回来，浏览器里没有内嵌视图，它们的后置条件本来就成立。它们不是用户点下去的动作，是内部让位。要求视图**做事**的 `load`、`scrape`、`resize` 仍然报错。

## Considered Options

- **全部静默 no-op**：界面最干净，但一旦某个降级不成立，症状是界面局部失灵而非报错，排查要从"哪个调用被吞了"开始。
- **同步抛出**而非返回拒绝的 Promise：预加载脚本里这些方法本来就返回 `ipcRenderer.invoke(...)` 的 Promise，同步抛出会改变调用契约，并让 effect 里的调用点直接崩掉界面。

## Consequences

控制台里会有噪音：任何一次走到降级路径的调用都会留下一条带方法名的拒绝记录，包括应用自己在启动时发出的那些（例如系统代理设置的读取，它的处理器在本地服务里根本没登记）。这是刻意的：噪音是可读的，静默不是。

映射的那一类需要谨慎：`app.getPlatformInfo()` 从 user agent 推断平台，因为渲染层用它决定标题栏是否自绘窗口按钮——答错了是肉眼可见的。但它推断不出架构和系统版本，那两个字段返回 undefined。用到它们的调用点（关于页、网络状态页）会显示空白而不是报错。
