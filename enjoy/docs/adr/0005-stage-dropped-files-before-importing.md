# 拖进浏览器的文件先落盘到 Library 暂存目录，再走同一个导入处理器

Desktop Enjoy 里导入一个本机文件只有一种形态：渲染层拿到一个路径，交给 `audios-create` / `videos-create`，模型把它复制或压制进 Library。渲染层和主进程共用一个文件系统，路径本身就是全部。

浏览器里没有路径。拖进来的 `File` 只有字节和文件名，`input type=file` 选出来的也一样。于是本地服务多出一个 Electron 里不存在的路由 `POST /files/:name`：把字节写进 Library 的 `cache/staging/<uuid>/<原文件名>`，返回落盘位置。拿到路径之后，导入走的是和粘贴绝对路径**完全同一个**处理器。

暂存副本是一次性的：模型会把它复制或转码进 Library，此后再也不看它。本地服务每次启动清空该目录。

## Considered Options

- **新开一个"从字节导入"的处理器**：要在模型层再写一条与 `buildFromLocalFile` 平行的路径，且两条路径的去重、元数据、压缩逻辑必须保持一致。落盘一次换掉这份重复，划算。
- **暂存到系统临时目录**：可行，但 Local Web Enjoy 的说法是"数据全部留在本机的 Library 里"，让导入的中间产物落在 Library 之外会削弱这句话，也让排查时多一个要找的地方。

## Consequences

导入一个大文件要先把它整个写一遍，磁盘上短暂出现两份。粘贴绝对路径的那条路不经过这里，也不产生上传流量——这正是它作为"超大文件退路"的意义。

`showOpenDialog` 在浏览器里也走这条路：它按 Electron 的契约返回路径数组，只是那些路径指向暂存目录而不是用户原本的位置。界面上会显示这个路径，看起来比 Desktop Enjoy 陌生，但调用契约是一致的。
