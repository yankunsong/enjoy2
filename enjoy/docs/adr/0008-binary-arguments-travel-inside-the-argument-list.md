# 二进制参数随参数列表以 base64 过桥，而不是另开一条上传

浏览器里录下的一段跟读，除了字节什么也不是——没有路径，没有文件。它跨过桥接层的方式是待在参数列表里：`recordings.create({ blob: { type, arrayBuffer } })`。

Electron 下这条参数走的是结构化克隆，`ArrayBuffer` 原样过去。本地服务这一侧参数列表是 JSON，而 `JSON.stringify` 把 `ArrayBuffer` 渲染成 `{}`——**不报错**。处理器于是读到一段长度为零的录音，报的却是"没有检测到声音"。这类失败最贵的地方不在于它失败，而在于它指向错误的方向。

跟读这条路上这样的字节有两处，不是一处。另一处是 Alignment：`echogarden.align(new Uint8Array(...), transcript, options)`。`JSON.stringify` 把 `Uint8Array` 渲染成一个以数字为键的对象，同样不报错，同样在处理器那边变成一个"认不出来的音频源"。**Timeline 正是从这里来的**，而 Timeline 是"点某一句让它单独循环"的前提——所以这不是顺手带上的第二个调用点，是这张票第一条验收标准的底座。

所以在桥接层把字节编成 base64，服务端解回来。编解码两半写在同一个模块里，两侧都只用 `atob`/`btoa`——浏览器和 Node 都有——所以线上格式只被声明一次，不会各写各的。

线上格式还要带上**是哪一种**：`ArrayBuffer` 还是 `Uint8Array`。两边的处理器分得清——Echogarden 的音频源收 `Uint8Array`，没听说过 `ArrayBuffer`——所以线上格式也必须分得清，光把字节送到不够。其余的 view（`Float32Array` 之类）没有任何调用点，遇到就**具名报错**，而不是悄悄按错的种类送过去；这是 ADR 0004 在别处的同一个做法。

## Considered Options

- **另开一条上传路由**，像 `POST /files/` 那样先把字节送过去、拿回一个路径再调用处理器。字节属于它所在的那次调用，分成两次意味着服务端要把两者重新对上；而 `/files/` 的字节本来就是一个文件，路径正是它要的东西，录音不是。
- **整条 IPC 改用 multipart 或 MessagePack**：为一个参数换掉整条线路的编码，其余 84 个处理器全部陪跑。
- **让渲染层自己先转 base64**：那要在渲染层加一个只有浏览器发行版成立的分支，正是 ADR 0002 不做的事。

## Consequences

base64 比原始字节多三分之一，这段开销走的是本机回环。一句跟读是几十到几百 KB，跨过去感觉不到；真正大的文件（导入的素材）走的是 `/files/`，不经过这里。

编解码穿透数组和纯对象，与 `media-url.ts` 的改写是同一套走法——两者现在共用 `traverse.ts` 里的那一次遍历：`Blob`、`File`、`Date` 这类有构造函数的值原样透传。

线上格式是"只有 `__binary__`、以及可选的 `__view__` 的纯对象"。判定要求**没有别的键**，否则一个恰好带同名字段的普通参数会被当成字节解掉。

回程没有做对称的编码：目前没有任何处理器把二进制原样返回给渲染层，返回的是 Library 地址，由 `GET /media/` 取。哪天有了，这个模块已经备好了另一半。
