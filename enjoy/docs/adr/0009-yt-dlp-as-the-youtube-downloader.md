# YouTube 下载改用 yt-dlp，二进制不由我们钉版本

原来的下载器是仓库里签入的一个 Go 二进制，构建于 2024 年 3 月。YouTube 早已拒绝它发出的请求，实测任何链接都返回 400——Desktop Enjoy 的 YouTube 导入在本票之前是坏的。仅仅升级那个二进制只是把同样的失效推迟几个月：跟得上 YouTube 的下载器，是那种把"跟上 YouTube"当作全部工作的下载器。

改用 **yt-dlp**，且**不把二进制签进仓库**。`youtube-dl-exec` 在安装时取当期发布版，`ENJOY_YT_DLP_PATH` 指向另一个——用户自己装的更新版本，或者测试用的替身。我们钉住的是这个 npm 包的版本，不是 YouTube 的解析逻辑。

调用形态沿用旧的那一套：外部进程、我们解析它的标准输出、代理走环境变量。先用 `--dump-single-json` 取一次描述（标题用作文件名，两条流的大小用作进度分母，链接不可用时在这里就失败），再下载。

## Considered Options

- **换一个纯 JavaScript 的解析库**（如 `@distube/ytdl-core`）：省掉一个二进制，但把"跟上 YouTube"的责任换成了另一个更新更慢的上游，且它一旦落后，我们除了等没有别的办法。外部二进制至少能被用户自己换掉。
- **继续签入二进制，只换成 yt-dlp 的**：仓库里多两个平台的几十 MB，而且我们的发布节奏（半年一次）比 YouTube 的变更节奏慢得多，等于把过期时间钉死在发布日。

## Consequences

安装时需要一次网络请求去取二进制；离线安装会缺这个文件，届时报错来自 yt-dlp 的缺席而不是一句笼统的下载失败。

画质由"取第一个含音频的流"改为显式 `bestvideo[height<=720]+bestaudio`，画面和声音分别下载后由本仓库已有的 ffmpeg 合并（`--ffmpeg-location` 指向 `ffmpeg-static`，而不是碰运气用 PATH 上的那个）。旧的 360p 是"找到第一个能用的就停"的副产物，从来不是选择。没有 720p 的素材（比如 2005 年的视频）走后面的兜底分支，拿到什么是什么。

yt-dlp 读 YouTube 的 player 需要一个 JavaScript 运行时，没有则警告"部分格式可能缺失"——720p 正在"部分格式"之列。它自己只找 Deno；我们额外把当前进程的 Node 指给它，这在 Local Web Enjoy 下总是成立的。Desktop Enjoy 下没有可指的 Node（`RunAsNode` fuse 是关的），只能让它去 PATH 上找。代价是 `--js-runtimes` 是个较新的选项：把 `ENJOY_YT_DLP_PATH` 指向一个旧到不认识它的 yt-dlp，每个链接都会失败。我们不去探测，因为那句失败正是 yt-dlp 自己写的、指名道姓的"no such option"，而会设这个变量的人也知道怎么改回来。

进度按字节报，`received` 和 `total` 从此在两个下载器里是同一个意思——旧实现里 `received` 这个名字装的是百分比，读它的三处组件因此各写各的算法。两条流各自从零开始计数，累计由这里完成，所以界面上的进度条不会走到一半退回去；分界由 yt-dlp 报的 format id 判定，而不是"字节数变小了"这种猜测。落地路径同样由 yt-dlp 自己说（`--print after_move:filepath`），省掉了在缓存目录里按文件名去猜的那一步——那一步会把上一次运行的残留当成这一次的产物。

超时是一个"沉默计时器"而不是一个总时长：yt-dlp 五分钟不说话才判定卡死，并以此为由报错。总时长上限会在慢网络上把一个长视频拦腰砍掉，然后只留下一个退出码——恰恰是本票要消灭的那种失败。

失败时把 yt-dlp 的 `ERROR:` 行原样送到界面。下载器过期、视频不可用、链接不成立，这三件事只有第一件是我们该修的，而包成一句"下载失败"之后它们长得一模一样。
