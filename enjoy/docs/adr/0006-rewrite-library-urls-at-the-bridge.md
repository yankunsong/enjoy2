# Library 地址在桥接层双向改写，两侧代码都不知道对方的写法

主进程把 Library 里的文件表述成 `enjoy://library/...`。Desktop Enjoy 为这个 scheme 注册了协议处理器，浏览器则完全不认识它——`<video src="enjoy://...">` 什么也不会发生。本地服务把同一批文件挂在 `GET /media/` 下。

改写发生在浏览器桥接层，且是双向的：处理器返回的结果里，`enjoy://library/` 开头的字符串换成 `/media/library/`；渲染层传进来的参数里，`/media/library/` 开头的字符串换回 `enjoy://library/`。回程这一半不是对称强迫症——渲染层会把拿到的 Media 地址原样传回处理器（转码、对齐、下载都吃这个地址），只改单向会让第二次调用找不到文件。

匹配的是**整个前缀**而不是 scheme 或路由名。回程改写作用在参数上，而参数里就有用户粘贴进来的本机绝对路径；`/media/` 在 Linux 上是真实的挂载点根目录，只匹配它会把 `/media/usb/x.mp3` 悄悄改成一个不存在的地址。

## Considered Options

- **在本地服务出口改写**：一处就能同时覆盖 IPC 应答和将来的推送。但那样主进程的返回值在离开自己进程时就已经是浏览器的说法了，服务端从此有一半代码在讲客户端的方言。
- **让渲染层自己判断**：要找出每一个用到 `src` 的地方并加分支，而 ADR 0002 的前提正是渲染层不为发行版分叉。

## Consequences

改写是按前缀匹配整个字符串做的，只穿透数组和纯对象。Blob、File、Date 这类有构造函数的值原样透传，不会被拆成属性包。

将来 SSE 推送落地时（本地服务推给浏览器的那条线），推送的消息体也带 Media 记录，需要在订阅侧接同一个改写——那时 `media-url.ts` 会有第二个调用点。
