# 推送走 SSE，消息体带原来的 channel 名

主进程会主动推东西给渲染层：数据库事务、通知、下载进度。Desktop Enjoy 从两个出口推——主窗口的 `webContents`，以及发起调用的那次 IPC 事件的 `sender`——两者在 Local Web Enjoy 里都已经被伪造成同一个汇（见 ADR 0001）。这条 ADR 记的是这个汇怎么过到浏览器。

用 SSE，不用 WebSocket。推送本来就是单向的，SSE 是浏览器内置能力，断线自动重连，不需要任何依赖；WebSocket 要引入一个服务端库，还要自己写重连。

消息体是**推送时的原样**：channel 名加参数列表。浏览器侧按 channel 名分发给已注册的回调，所以 `onNotification(cb)`、`db.onTransaction(cb)`、`download.onState(cb)` 这些签名一个字都不用改，上层组件完全不知道自己身处浏览器。这是整条链路的目的——不是把推送搬过来，而是把它搬过来且**不留下痕迹**。

## Considered Options

- **WebSocket**：双向能力用不上，代价是一个依赖和一套自己写的重连逻辑。
- **轮询**：进度条会变成一跳一跳的，且每个 channel 都得想一个"最近发生了什么"的查询接口——推送本来没有这个概念。
- **给每个 channel 一条 SSE 路由**：几十条连接换不来任何东西，浏览器对同源并发连接还有上限。

## Consequences

浏览器侧订阅的是一条连接，断了由 `EventSource` 自己重连，订阅者不感知——这也是验收里"断开再恢复后推送自动恢复、无需刷新页面"能成立的原因。

**断线期间的推送不补发**：消息不带 `id:`，服务端也不留重放缓冲。恢复的是通道，不是错过的消息。补发要求服务端为每个订阅者存一段历史，而唯一会因此丢掉的是"断线那几秒里完成的导入"——重新打开那个列表就能看到它。为一次性自用工具养这套历史不值当。

推送的消息体里带 Media 记录，所以订阅侧要接上 `media-url.ts` 的改写，这正是 ADR 0006 结尾预告的第二个调用点。

前端开发服务器的代理里这条路由要**锚定**成 `^/events$`：桥接层自己有一个 `events.ts`，用前缀匹配会把它一起吞掉。

序列化不了的推送被丢弃并记一条日志，而不是让整条流断掉——一个推送点的 bug 不应该带走其他所有 channel。
